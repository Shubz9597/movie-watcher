# M1.3 / M1.4 feasibility packet (prepared, NOT executed)

Date: 2026-09-11. Purpose: give the M1.3 iPhone spike and the M1.4 transport decision a factual starting point. This packet contains NO device results and does NOT choose an architecture. Nothing here completes M1.3/M1.4.

## 1. Actual server stream surface (verified in source, not on a device)

The backend (`torrent-streamer`) exposes ONE playback transport today: **progressive HTTP byte-range streaming of the torrent file**. There is no HLS/DASH and no transcoding anywhere in the tree.

- `GET /stream?infoHash=<ih>&fileIndex=<n>` (internal/httpapi/handlers.go `handleStream`)
  - `Accept-Ranges: bytes`; `Range` request → **206 Partial Content** + `Content-Range: bytes s-e/size`; invalid range → **416** with `Content-Range: bytes */size` (handlers.go:442-487).
  - `Content-Type` from file extension (`mime.TypeByExtension`, fallback `application/octet-stream`), `Content-Disposition: inline`, `Cache-Control: no-store`, `X-File-Index`, `X-File-Name`.
  - Headers are flushed BEFORE buffering completes (http.NewResponseController.Flush), so a player sees status/headers during slow prebuffer.
  - Buffer controller per (cat, infoHash, fileIndex) with play/pause target seconds; 4K detection raises targets; probe ranges are not treated as playhead moves.
- Lease/session: `/watch/open`, `/watch/ping`, `/watch/close` (lease manager, admission control, max active titles).
- Progress/resume: `/v1/session/start|heartbeat|ended`, `/v1/resume`, `/v1/resume/source`, `/v1/resume/source/probe`, `/v1/continue`, `/v1/continue/dismiss`, and `/v1/resume.m3u` (served as `audio/x-mpegurl` — a resume playlist wrapper for external players, not an HLS live pipeline).
- Support: `/add`, `/files`, `/prefetch`, `/stats`, `/buffer/state`, `/buffer/info`.
- Subtitles: subtitle_handlers (HTTP fetch/caching path; `SUB_CACHE_DIR`). Format conversion (extract → VTT) exists in the tree for the renderer path; whether it covers iPhone needs device testing.
- CORS: versioned browser/mobile surfaces use the explicit allowlist; `Range` is an allowed preflight header (cors.go). The media endpoints themselves are consumed by native players and the desktop shell.

## 2. What this transport means for iOS

- A progressive 206-range stream plays natively in Safari/WKWebView **only in containers Safari can demux**: MP4/M4V (H.264/AAC) reliably; MKV generally NOT; HEVC in MP4 on modern devices only for hardware-supported variants; ASS/SSA subtitles will NOT render (Safari supports WebVTT sidecar only).
- Bitrate/latency behavior against a partially-downloaded torrent (buffering controller, header flush) is exactly the unknown that REQUIRES a device test; desktop MPV tolerance proves nothing about AVPlayer.
- Interruption (call, backgrounding, lock), background audio, and resume positioning use AVPlayer/AVAudioSession semantics that do not exist on desktop.

## 3. Representative containers/codecs that require device testing (M1.3 matrix)

| Container | Video | Audio | Subs | Expected Safari/native | Needs device proof |
|---|---|---|---|---|---|

| MP4 | HEVC (hvc1) | AAC | mov_text | likely on A12+ | codec level support |

Subtitle sidecar path: the app's fetched SRT/ASS must be converted to WebVTT for Safari; native MPV path differs. This split is a planned M1.3 spike output, not yet built.

## 4. What can be tested in Safari/browser vs what needs a native player

Testable in Safari (private tailnet, no packaging):
- 206/Range behavior of `/stream` against a real torrent from Safari's media element (MP4 sample), seek behavior, stall/recovery when prebuffer drains.
- WebVTT subtitle sidecar loading.
- Resume endpoints round-trip (`/v1/resume`, heartbeats) from a web client.

Requires the native thin wrapper (or native player):
- AVPlayer/AVAudioSession interruption handling, background audio, lock-screen controls, Picture-in-Picture.
- Non-Safari containers (MKV etc.) via a player library (e.g. VLCKit/MPV-based) or a transcode/HLS pipeline.
- Fullscreen/airplay behaviors and real performance (ARM64 Radxa equivalence is a separate M6 gate).

## 5. Proposed thin-wrapper / player experiment (for M1.3 execution — decision deliberately deferred)

1. Minimal WKWebView shell (no React Native) loading the production browser bundle from the private tailnet origin; library/progress flows unchanged (BFF contract).
2. Add ONE native hook: an `onPlaySource(url)` bridge that either (a) presents AVPlayer for MP4/HLS-capable sources, or (b) hands the URL to an embedded VLC/MPV layer. Record which sources each path plays.
3. Point it at a REAL seeded torrent on the homeserver/Radxa; capture the M1.3 matrix (play/seek/subtitle/stop/resume/interruption).
4. Outcome feeds the M1.4 decision: direct-play-only vs bounded HLS/transcode vs embedded third-party player — with measured costs and rollback, per the tasks.md M1.4 row. **Do not choose before the matrix exists.**

## 6. Isolated Mac+iPhone/Xcode gate

M1.3 cannot start without: a macOS machine with Xcode + a (free) Apple ID for a development-signed install on one physical iPhone via cable; the iPhone on the tailnet (Tailscale iOS app) or the Mac on it. Windows cannot produce the iOS shell build. This is the hard gate blocking M1.3; it does not block M2–M4 work.

## 7. Known server-side gaps for mobile playback

- `/stream` has no authentication/token; it binds 127.0.0.1 today and is exposed only via private tailnet Serve. Mobile direct access (without Serve) would need the lease/origin story revisited — M1.4 scope, needs a contract decision.
- No byte-range cache coordination with the buffer controller for multi-client seek storms (single-household scale probably fine; measure on device).
- `resume.m3u` is built for external players; AVPlayer needs its own resume plumbing (timeScale/seek-into-range), to be proven in the spike.
