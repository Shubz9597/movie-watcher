Executed: 2026-09-09 (destination PC, branch `001-build-torwatch-version` @ `5e9c648`). Scope: the bounded compatibility child task M3.1.1 ONLY — implement media-qualified canonical ids `tmdb:movie:N` / `tmdb:tv:N` across producers and affected consumers, per [m3.1-identity-contracts.md](m3.1-identity-contracts.md) §2. **No Library storage, migrations, write endpoints, capability advertisement, or progress rekeying was added.** M3.2 was not started.

## 1. Server producers (Go, `torrent-streamer`)

`internal/catalog/tmdb.go`:

- `titleFromMedia` emits qualified ids: `tmdb:movie:N` for movies, `tmdb:tv:N` for series AND for TMDb-classified anime (anime is a classification over the structural media type, never a third namespace). `ProviderIDs["tmdb"]` mirrors the qualified external id (`"movie:N"` / `"tv:N"`), so catalog id = namespace + qualified external id. Applies to Search, Section, SectionPage, GenreSection and Detail alike.
- `splitTMDbExternalID` (new) splits the optional media qualifier from the numeric id.
- `Detail` accepts the qualifier and probes ONLY the requested endpoint: `tv:N` → `/3/tv/N`, `movie:N` → `/3/movie/N` — **never a cross-media fallback, including failure cases** (qualified tv 404 stays `ErrNotFound` even when a movie with the same number exists). The unqualified numeric form keeps the documented deterministic movie→tv probe order as a read-only legacy alias.
- `Episodes` always resolves through the numeric tv endpoint and handles both the qualified and legacy external-id forms; episode ids embed the requested title-id form (`tmdb:tv:N:s:e` for qualified requests, `tmdb:N:s:e` for legacy alias requests), and `ProviderIDs` stays qualified when the request is qualified.
- Merging is untouched: the merge key remains normalized title + year + **type** (`cache.go`), so qualified ids cannot cross-merge movie/series/anime.
- Caches: detail cache keys are the full opaque id (`detail:tmdb:tv:123` vs `detail:tmdb:123` are distinct entries; the alias and the qualified id never pollute each other). Episodes cache keys are the provider-id-set based canonical key — qualified and legacy sets are distinct. No cache change was needed; behavior verified by tests.

## 2. Server consumers

- `Service.Detail` / `Service.Episodes` (`service.go`) parse qualified ids through the existing `ParseTitleID` opaque-id path (`tmdb:tv:123` → namespace `tmdb`, external `tv:123`) — no service change needed; proven by `TestIdentityQualifiedServiceDetailResolvesEachMediaType`.
- `httpapi` handlers pass the full id through opaquely (`/v2/catalog/titles/{id}` accepts the extra colon segment); a qualified detail response emits the qualified canonical id.
- Legacy alias behavior preserved end to end for old clients: unqualified `tmdb:N` still resolves movie-first and now emits the **qualified truth** (`tmdb:movie:N`) — old clients treat ids as opaque and keep using the numeric card id, which is unchanged.

## 3. Client consumers (`electron-app`)

- `catalog-bff.ts` `catalogIdForSeriesId`: **qualifier preserved** — `tmdb:movie:123` → `tmdb:movie:123`, `tmdb:tv:456` → `tmdb:tv:456` (was lossy `tmdb:N`). Continue-service enrichment now addresses the requested media type; progress seriesIds are exactly the catalog id form, so no progress rekeying and no ordering change.
- `catalog-bff.ts` `backendTitleToCard` and `adapters/media.ts` `detailFromBackendTitle`: strip the qualifier from qualified tmdb external ids for the numeric display/navigation id, so cards keep numeric `id` while `catalogId` stays media-qualified opaque.
- `TitlePage.tsx` `loadBffTitle`: detail requests use the qualified id built from the route's explicit media namespace (`kind` / `provider=tmdb` + `mediaKind`): `tmdb:movie:N` for movie and tmdb-anime-movie routes, `tmdb:tv:N` for tv and tmdb-anime-series routes. Direct/reloaded links carry the same `kind`+`id` route params, so reloads rebuild the same qualified id; no route ever rebuilds the ambiguous `tmdb:N`.
- `PlayerPage.tsx`: bff metadata requests use `tmdb:movie:N` / `tmdb:tv:N` derived from the route's `cat` namespace (movie/tv); the anime/anilist path is unchanged.

## 4. Rollout compatibility (honest limits)

- **Old client + new server**: works. The unqualified alias keeps the movie-first probe (regression-tested); responses now carry qualified ids, which old clients treat as opaque; numeric card ids are unchanged.
- **New client + old server**: TMDb detail/episode lookups FAIL (the old server would probe `/3/movie/tv:N` → 404 → `/3/tv/tv:N` → 404 → `title_not_found`). This is a documented limitation: server-side alias support alone does NOT prove both directions compatible. Clients surface the truthful error; no silent fallback. Deploy the new server binary before/with the new client.
- Renderer default remains `catalogSource=renderer` with its own direct-provider path (unchanged, unqualified upstream calls); the alias keeps those parity fixtures green.
