# M4.1 evidence — bounded server-side recommendations implemented

Executed: 2026-09-10 (branch `001-build-torwatch-version` @ `5e9c648` + preserved M3.1.1–M3.4 diffs). Scope: M4.1 ONLY — the server-side recommendation service and `GET /v2/recommendations`. **No client UI (M4.2), no ML/embeddings/external AI/profiles, no new recommendation infrastructure.**

## 1. Contract

`contracts/recommendations-api.md` (new) — finalized narrowly from plan.md §Light recommendation rules and the recommendation proposal in library-api.md: `GET /v2/recommendations?limit=n` (default 20, min 1, **max 20**, invalid → 400 `invalid_request`), response `{revision, fallback, degraded, generatedAt, items:[{canonicalId, type, title, year, artwork, reason:{code, text, seedCanonicalId}}]}`, reason codes `seed_genre` (grounded in the most recent contributing favourite seed) and `popular` (zero-score filler / fallback), capability `recommendations.basic.v1` advertised only when the service is wired.

## 2. Implemented behavior

- **Seeds**: the up-to-20 most recently favourited titles (`library.Store.FavouriteSeeds`). Seed genres resolve through the existing catalog detail path — at most ONE call per seed per cache build (`CatalogSeedGenres` adapter); a seed without genre metadata contributes nothing but is still excluded from results.
- **Candidates**: `catalog.TMDb.PopularCandidates` (new `CandidateProvider` capability) — weekly trending pages (bounded ≤5 pages) deduplicated, with numeric genre ids mapped to names via the two TMDb genre-list lookups, so the pool carries genres with ~6 upstream calls per build, never per candidate. Provider popularity rank = pool position. Anime classification survives the mapping.
- **Scoring**: per candidate = number of DISTINCT seeds sharing ≥1 provider-qualified normalized genre (`"<namespace>:<normalized genre>"` — cross-provider genre matching stays untested/disabled per plan). One seed contributes at most one point; repeated genres never inflate. Genre resolution failure for a seed does not error the request.
- **Exclusions/dedup/order**: every favourite AND watch-later id excluded (real library data); candidates deduplicate by canonical id; ordering is score desc → provider rank asc → canonical id asc (deterministic).
- **Cache**: in-memory, keyed by `(household revision, candidate-cache version)`, TTL 15 minutes. Effective mutations advance the revision → next request recomputes; NO-OP writes leave the revision unchanged → cached result served unchanged (no invalidation). Restart loses the in-memory cache (harmless; recomputed on demand).
- **Never blocks**: a candidate/library failure serves the last computed result truthfully `degraded` (or a truthful empty degraded section when nothing was ever computed).
- **Composition root** (`cmd/vod/main.go`): the service is wired ONLY when the library store is open AND a catalog provider implements `CandidateProvider`; `recommendations.basic.v1` is advertised only then. Handler registration is a no-op without the service (older servers 404 the route).
